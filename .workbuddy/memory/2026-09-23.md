## 发现源支持 topics 页面

弘道：「发现要支持topics 页面，例如 https://github.com/topics/ai-agent」。
读作「把 topics 页当成一种发现源」——发现源本来就是一条 URL。

**改动**（8 个文件）：

- 新增 `github/entry.rs`：`RepoEntry`（原 `TrendingEntry` 改名）+ 两个解析器共用的工具
  （`repo_from_href` / `parse_count` / `collapse_whitespace` / `element_text` /
  `stars_from_counter` / `selector`）。原来这些小工具在 `trending.rs` 里，topics 要用就得
  复制一份，所以先抽出来。
- 新增 `github/source.rs`：`SourcePage::{Trending, Topic{slug}}` + `of(url)`，
  以及给用户看的 `UNSUPPORTED_URL_HINT`。认不出的地址返回 `None`。
- 新增 `github/topic.rs`：`parse_topics`。
- `github/mod.rs`：`fetch_trending` → `fetch_source`（按 `SourcePage` 分派）。
- `discovery/runner.rs`：改调 `fetch_source`，条目类型换 `RepoEntry`。
- `discovery/model.rs`：`validate_source_url` 增加「这一页认不认得」的检查。
- `discovery/sources_view.rs`：`suggest_name` 分两类（topics 出「话题 · ai-agent」，
  带 `?l=python` 就是「话题 · ai-agent · python」）；输入框 placeholder 换成 topics 的例子。

**why**：

- 类型只从 URL 形状推，不加持久化字段——加了就会出现「改了地址忘了改类型」。
- 认不出的地址**添加时就拒掉**，不留到运行时每轮报「结构可能已经变化」：
  那句话会把「我们不支持这个地址」说成「GitHub 改版了」，让人往错的方向查。
  运行时仍再拦一次（地址可能是手改配置文件写进去的）。
- `/trending/developers` 也拒掉：那是一份**人**的榜单，结构完全不同。
- 拒绝时要求主机是 github.com：两个解析器都是对着它写的。

**真实页面里的三个坑**（都是先抓整页 HTML 看出来的）：

1. **星数计数器显示的是缩写**。topics 卡片上 248198 星写成 `248k`，直接读文本（原来
   trending 那么读）会得到 248 —— 一个看着像真数据的错数。完整数字在
   `title="248,198"` / `aria-label="248198 users starred this repository"` 上。
2. **卡片的 tab 栏里有重复的仓库链接**。Code / Issues / Pull requests 里 `Code` 也指向
   `/owner/repo`，选择器不限定在 `h3` 里就会把每张卡片解析成两条。
3. **`tmp-` 前缀的工具类不能当锚点**。GitHub 正把 `mr-3` / `px-3` 逐个改成 `tmp-mr-3` /
   `tmp-px-3`，同一张卡片上两种混着出现。改成只靠结构与语义标记。

**验证**：

- `cargo test` **246 passed / 0 failed / 2 ignored**（231 → 246）。
- `cargo clippy --all-targets` 无警告。
- 除了单测里的真实片段，**另拿三份整页样本跑了一遍解析器**（topics 两页 + trending 一页，
  用 `curl -sL -A "<浏览器 UA>"` 抓）：topics 各 20 条、trending 20 条，
  描述 / 语言 / 星数都对得上。探针用完即删，样本也没留。
  这一步值得：片段只能证明选择器写对了，证明不了它在整页上不会多匹配。
- 顺手确认 trending 的解析现在仍然成立（`article.Box-row` 20 个、`h2 a[href]` 正常），
  这次重构没有碰坏它。

**没做**：topics 页的话题名没有落成仓库的标签（例如从 `/topics/ai-agent` 发现的仓库
自动挂 `ai-agent` 标签）。那是个独立决定，先问过再说。

## 从话题页发现的仓库自动挂上话题名做标签

接上一条问的话，弘道回「要」。

**改动**（6 个文件）：

- `github/source.rs`：新增 `SourcePage::tags()`（Topic → `[slug]`，Trending → 空）与
  `tags_for_source(url)`；`github/mod.rs` 转出。**标签名从地址推，没有「源 → 标签」映射表。**
- `discovery/runner.rs`：`SourcePlan` 多一个 `tags`（在 `plan()` 里按地址算，和其他配置
  一起快照）；`absorb` 拆成异步外壳 + `absorb_entries`（`&mut Library`），后者把标签
  先建进词表、再逐条入库。返回值从 `(usize, usize)` 换成 `Absorbed{added, skipped, missing_tags}`。
- `discovery/sources_view.rs`：源那一行加一句「新发现的仓库会自动挂上标签：ai-agent」
  （`SourceRow::tags_text`，纯函数，有测试）。
- `library.rs`：**修了 `add_repo` 的一个洞**（见下）。
- README：新段「从话题页发现的仓库会自动挂上话题名做标签」+ 三条口径；测试数 253。

**口径**：

- 只给**这一轮新入库**的仓库挂。`add_repo` 对已在库里的返回 `AlreadyPresent`、
  一个字段都不碰——否则用户手工摘掉的标签下一轮又长回来，等于删不掉。
- 标签先走 `add_name(TaxonomyKind::Tag, slug)` 建进词表，再 `repo.tags = tags`。
  `add_repo` 是拿名字去词表换 id 的，**词表里没有的名字会被静默丢掉**。
- 建不出来（名字超 40 字上限 / 写库失败）记进 `Absorbed.missing_tags`，由 `run_plan`
  拼进这一轮的错误里说一句——少挂一个标签但闷着不说，是最难查的那种。
- trending 不带标签：它是榜单不是主题，挂 `weekly` 没意义。

**顺手修的洞**：`Library::add_repo` 只把「词表里有的名字」换成 id 写库，却把**原始
`repo.tags` 整份塞进内存镜像**。于是词表外的名字会留在内存里：界面上显示一个**重启就
消失**、而且点不着（不在任何筛选项里）的标签。我的测试先撞上了这个（断言「没挂上」失败）。
现在 `add_repo` 按词表过滤 + 换成词表里的写法，和 `set_repo_tags` 一个口径。

**已知后果**（写进 README 了）：话题名跟着地址走，所以在词表里删掉那个标签，只要源还在
下一轮会重建（可能是空标签）；把它改名，下一轮会新建一个同名标签。

**验证**：`cargo test` **253 passed / 0 failed / 2 ignored**（246 → 253：source 1、
runner 4、sources_view 1、library 1），`cargo clippy --all-targets` 无警告。

本批未提交（与本文件上半那条 topics 支持一起压着）。
