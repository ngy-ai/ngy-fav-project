## ngy-fav-project 从零建成并真机验证通过

GitHub 仓库收藏/发现桌面程序，gpui-kit 实现。22 个源文件、4732 行、42 个测试通过、clippy 无警告。

### 三块需求与落地位置

- 项目管理（名称/原始描述/汉语描述/发现时间/创建时间）→ `src/repos/model.rs` + `src/repos/repos_view.rs`
- 仓库发现（trending 类地址可增删）→ `src/discovery/model.rs` + `src/discovery/sources_view.rs`

### 真实踩坑（都已在代码里修掉，改这块时注意）

1. **`is_due` 把「元数据缺口」和「完整运行」混成一个 bool**，导致每 60 秒重抓一次 trending，
   还把上一次 `added: 21` 的成功记录覆盖成一次 `timeout: global` 失败。
   修法：`DueKind::{Full, Metadata}` 两种触发分开；元数据轮不写 source record。
   回归测试：`metadata_gap_triggers_a_metadata_round_not_a_full_run`。

2. **匿名 GitHub API 只有 60 次/小时**，固定 60 秒重试一批 8 个 = 480 次/小时，几分钟烧光配额。
   修法：`retry_seconds_for(stall_rounds)` 指数退避，封顶 15 分钟，只在本轮「一个字段都没补上」时增长。

3. **元数据补全串行太慢**（21 个实测 40+ 秒，`phase` 全程锁 Running，用户点什么都被拒）。
   修法：`buffer_unordered(METADATA_CONCURRENCY = 4)`。实测 21 个 100 秒内补齐，配额消耗恰好 21 次、零重试。

### gpui-kit 的 API 事实（版本坑）

- **依赖固定 `gpui-kit = "0.6.4"`**。最初按 0.6.1 写，核对 registry 源码时发现 0.6.1 与 0.6.4
  在 `dialog/footer.rs`、`switch.rs`、`theme/theme_color.rs` 等处有差异，已升到 0.6.4；
  以后查 API 一律看 0.6.4 的源码，别照 0.6.1 的资料写。
- **`Entity::update` 直接返回 `R`**（实体不存在则 panic）；**`WeakEntity::update` 返回 `Result<R>`**。
  给前者多写一个 `.unwrap_or` 会报 `no method named unwrap_or found for type bool`。
- **`use gpui_kit::*` 会把 GPUI 的 `#[gpui::test]` 带进来、盖掉 std 的 `#[test]`**。
  测试模块里要补 `use core::prelude::v1::test;`（见各 `mod tests` 顶部注释）。
- 滚动要在带 id 的容器上（`div().id(..)`），普通 `v_flex()` 没有 `overflow_y_scroll`。
- `Dialog::footer(..)` 忽略 `button_props`；`DialogAction` 派发 `Confirm`，`DialogClose` 负责关闭。

## 添加应用图标

- `tools/make_icon.py` 生成 `assets/icon.ico`（16/32/48/64/128/256 六个尺寸）与 `icon.png`。
  深蓝灰圆角底 + 金色五角星；在 4 倍尺寸上绘制再降采样，边缘自带抗锯齿。
- `build.rs` 用 `winresource` 把 .ico 嵌进 exe，同时写 VERSIONINFO（版本号读 `CARGO_PKG_VERSION`）。
- **为什么必须嵌 exe**：gpui 的 `WindowOptions::icon` 注释写着 "X11 only"，
  Windows 的窗口与任务栏图标只认 exe 资源段，应用层设不了。

### 坑：winresource 默认探测要调 reg.exe，被本机安全策略拦掉

现象：`嵌入图标失败：系统找不到指定的路径。(os error 3)`，
同时 stderr 出现「PROGRAM BLOCKED BY SECURITY POLICY: reg.exe」。

原因：`WindowsResource::new()` → `get_sdk()` → `reg.exe query HKLM\...\Windows Kits\Installed Roots`，
reg.exe 在黑名单里启动失败，SDK 路径为空，于是 rc.exe 找不到。

修法：build.rs 自己扫 `C:\Program Files (x86)\Windows Kits\10\bin\<版本目录>\x64\rc.exe`
（目录名字典序即版本序，取最大那个），再 `set_toolkit_path()` 显式告知，绕开注册表。
`RC_PATH` 环境变量若已设置则优先尊重。找不到 SDK 只发 `cargo:warning`，不阻断构建。

### 验证 exe 资源的办法（本沙箱可用）

`Add-Type`（.NET 编译）和 `Get-Process` 都被安全策略拦，PowerShell 这条路走不通。
改在 Python 里直接做二进制比对：

1. 解析 ICO 的 ICONDIR，取出每个尺寸的图像块字节；
2. 在 exe 里 `bytes.find(blob)` —— 6/6 全部命中，偏移 52,968,792 起连续排列；
3. VERSIONINFO 的中文串按 UTF-16LE 搜索，同样命中。

另外 `cargo:rerun-if-changed` 有效：touch 图标后 exe 会重新链接。

**但监视目标已从 `assets/icon.ico` 改为 `assets` 目录**（同日改）：
监视单个文件时，如果首次构建它还不存在，cargo 会把「缺失」写进指纹，
之后再生成图标**也不会重跑 build.rs** —— 表现是图标永远嵌不进去、输出里只有那条
旧警告（cargo 重放缓存 warning）、`cargo build` 秒过。改成监视目录后新增文件也会触发。
已实测：改目录后「删图标 → build → 恢复图标 → build」能正常重建并嵌入。

### 本机环境坑（会反复踩）

- **Git Bash 的 `/tmp` 指向 `C:\WINDOWS`**，而 Python 把 `/tmp/x` 解析成当前盘的 `\tmp\x`。
  写临时文件一律用明确路径（如项目 `target/` 下），别用 `/tmp`。
- `Add-Type`、`reg.exe` 在安全策略黑名单里，别写依赖它们的东西。
- 给 Python 传脚本路径要用 `C:/Users/...` 原生路径。传 `/c/Users/...` 会被解析成
  相对路径 `E:\c\Users\...` 而报 `Errno 2`。

