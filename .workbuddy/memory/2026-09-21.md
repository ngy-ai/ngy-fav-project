## 真树 + 分页 + SQLite（需求：分类是树，仓库中要分页，后台使用 sqlite 数据库记录）

**这一轮推翻了上一轮的两个决定**：分类从「路径字符串 + 现算层级」改成 `parent_id` 真树；
持久化从 `library.json` 单文件换成 SQLite。改动面很大，`library.rs` 整个重写。

**存储层（新增 `src/db/`，6 个文件）**

- `mod.rs`：`Db { conn }` + `DbError{Sqlite,Io,Format,SchemaTooNew}`，`open` / `open_in_memory` /
  `transaction`（`unchecked_transaction`，因为 `&self` 不是 `&mut`）。
- `schema.rs`：6 张表 + `SCHEMA_VERSION=1`；`PRAGMA foreign_keys=ON`（**不打开级联删除完全失效**）、
  `journal_mode=WAL`、`synchronous=NORMAL`；`found > supported` 时返回 `SchemaTooNew` 硬失败不写入。
- `repos.rs`：`SELECT_COLUMNS` / `ORDER_BY` 常量 + `read_row` 按列下标取值（**两处必须一起改**）+
  `attach_tags` 批量补标签（避免 N+1）；`query_page`（LIMIT/OFFSET + 单独 COUNT）；
  `like_pattern` 转义 `% _ \` + `ESCAPE '\'`。
- `taxonomy.rs`：`name_key` 列存 Rust 侧小写化后的名字（**sqlite 的 `lower()` 只认 ASCII**）；
  同级唯一靠 `UNIQUE(parent_id, name_key)`，父为 NULL 时用 `ifnull(parent_id,0)` 参与索引。
- `legacy.rs`：旧 JSON 一次性导入，整批一个事务。

**真树（`taxonomy/tree.rs` 纯逻辑 + `db/taxonomy.rs` 读写）**

- `CategoryNode{id,parent,name,position}`，`CategoryTree` 里 `nodes` 恒按 `(position,id)` 排好，
  所以 `children(parent)` 取出来就是有序的。
- 纯函数都在 tree.rs：`segments/path/depth/subtree/is_within/find_path/sibling_named/flatten/
  insert/set_name/set_parent/remove_subtree`。`flatten` 用 `HashSet<i64>` 防重，
  游离节点也补在最后画出来。
- `taxonomy/model.rs` 瘦身：删掉 `is_within/parent_path/ancestors/leaf/depth/tree_order/dedupe`，

**Library 改成写穿**：删掉 `LibraryData` / `persist()` / `normalize_taxonomy()`。
所有修改走 `write(|db| ...)`：**库写成功才改内存**，失败记进 `save_state`（界面顶部横幅报错）。
唯一的例外是分类树：写成功后 `reload_categories()` 整批重读（表小，增量容易漏）。

**分页**

- `RepoQuery{search,category,page,page_size}` / `RepoQuerySpec` / `RepoPage{rows,total,page,page_size}`
  + `page_count/has_next/first_index/...` 都在 `repos/model.rs`。

- `CategoryScope::Subtrees(vec![])` 编译成 `WHERE 0`：**筛选一个已不存在的分类宁可空着，也不要静默变成「全部」**。

`renaming_onto_a_new_parent...` 那条测试的期望值跟着改了（新建出来的上级排在末尾）。

## 配额用完就停（需求：发现 github 访问配额用完后，就不要请求了，发现任务直接结束）

### 根因：403 上的配额头被整个丢掉了

旧代码在非 2xx 时走 `ureq::Error::StatusCode(code)`，**响应头与正文一起丢**，
`HttpError::Status` 只剩 `{code, url}`。于是撞配额时只能看到一个光秃秃的 403：
判断不出是不是配额、也不知道要等多久，只能换个仓库再试一次——**把本来就见底的配额
烧得更干净**。这才是「配额用完还在打」的真正原因，不是缺一个 `break`。

修法：`agent()` 加 `.http_status_as_error(false)`，让 4xx/5xx 也走 `Ok(response)`，
`blocking_get` 统一读头读正文，再自己转成
`HttpError::Status { code, url, rate_limit_remaining, rate_limit_reset, body }`。
`HttpResponse` 加 `rate_limit_reset`。头要在 `body_mut()` **之前**读（`&response` vs `&mut`）。

- **重定向不受影响**：`run.rs` 里按 `status().is_redirection()` 单独处理，
  `http_status_as_error` 只在 `run.rs:128` 作用于最终响应，两者不耦合。特意去查了源码。
- `body` 只留开头 200 字符（`body_excerpt`，按 `is_char_boundary` 截，别切在多字节字符中间），
  用来认二级限流的 `rate limit` 关键字。

### 判定与闸门（新增 `src/github/rate_limit.rs`）

- `RateLimit::from_response(status, remaining, reset_at, body)` 三条判据：
  `remaining == Some(0)` / 429 / **403 且正文提到 `rate limit`**。
  **光看 403 不行**——令牌没权限、仓库被下架也是 403，等多久都不会好。
- `blocked_until(now)`：优先用 `X-RateLimit-Reset`，没有就 +60 秒（二级限流），
  最后 clamp 到 `now + 3600`（防中间设备把 reset 改写成远期值，锁死发现功能）。
- `RateLimitGate` 内部 `Rc<Cell<Option<i64>>>`，**clone 共享状态**——`run_plan` 里
  clone 进各 future 的那份 `trip()` 了，`runner` 持有的那份立刻跟着变。
  只在 GPUI 单线程执行器里访问，不需要原子量。
- `trip` 合并时**先滤掉过期的旧值再取 max**，否则一个已过期的远期值会「接住」新的一次拉闸，
  等于没拉。

### 停在哪几层

1. `decide` **开头**就检查 `rate_limit_until`，没恢复直接 `None`——连**一轮完整运行**都不起，
   不只是停掉补全那一段。放最前面，因为配额是硬约束。
2. `run_plan` 的 sources 循环每轮开头再查一次闸门；
3. metadata 那批**在每个 future 发出去之前**查闸门，所以闸门一拉下，还没启动的就停在那儿。
   已经在飞的拦不回来，上界是 `METADATA_CONCURRENCY`（=4，注释里写明了）。
4. **配额掐断的轮不算「无进展」**（`stalled` 多一个 `&& !blocked_by_quota`），
   否则恢复时刻到了还要再叠一层退避，用户以为坏了。
5. `run_now` / `refresh_metadata_now` 先 `clear()` 闸门：用户主动点时多半刚填了令牌
   （60 → 5000）。真没恢复，第一个请求 403 会立刻再拉上，代价一个请求。

### 界面

`sources_view` 里 `rate_limit_until()` 有值时**不再显示「下次自动运行」**——那个时间到了
也不会跑，摆着只会让人等一件不会发生的事；改成在同一行位置显示「已停止联网，约 N 分钟后
（HH:MM 起）自动恢复」。另外 runner 每轮巡检都跑 `sync_rate_limit_flag()`，
闸门开合那一刻补一次 `notify`——否则恢复时刻到了却正好没活干时，界面会一直挂着那句过期的提示。

## 令牌申请入口（需求：github 访问令牌怎么申请？同时要加在设置旁边）

**先查官方文档再写文案**——网上的博客相互矛盾（有篇说「必须用 classic，fine-grained 不行」），
而官方文档写得很清楚：

- 未认证 60 次/小时（**按 IP**），认证 5000 次/小时（**按用户**）。
- classic：「A token with no assigned scopes can only access public information.」
- fine-grained：「Tokens always include read-only access to all public repositories on GitHub.」
  —— 公开仓库只读是令牌自带的，权限全留 `No access` 也照样能读。

所以**两种都行、都不用勾任何权限**，本项目只读 `/repos/{owner}/{repo}`。
（顺带印证了配额那轮的实现：官方说二级限流不带 `x-ratelimit-remaining`，
`remaining=0` 才等 `x-ratelimit-reset`，否则至少等 1 分钟。）

- `settings_view.rs` 令牌那栏加「去申请」按钮（`IconName::ExternalLink` + `cx.open_url`），
  指向 `https://github.com/settings/tokens`——**列表页而不是新建页**，已有令牌的人不必再走一遍

### 环境坑（重要）：沙箱里的 cargo 会卡在文件锁上

现象：`cargo build` 超过 20 分钟不出结果，日志只有一行 `Compiling ngy-fav-project`；
`Blocking waiting for file lock on package cache` / `build directory`；rustc 起来后
**10 秒 CPU 增量 +0.0s**（是等，不是慢）。

排查与结论：

- 宿主上直接 `rustc` 编一个最小程序 **0.5 秒**成功 → 不是 rustc 或安全软件的问题。
- `Get-CimInstance Win32_Process -Filter "Name='cargo.exe'"` 看命令行，发现有外部的
  编译循环在反复起进程（`cargo test --lib --locked <name>:: --no-fail-fast`，带
  `--no-fail-fast` 是 IDE 测试运行器的特征），它们持有锁并把 `target`/`package cache` 锁住。
- 处理：清掉卡住的 cargo/rustc，**改用宿主 PowerShell 跑**（本机沙箱工具跑 cargo 会一直排队）。
  干净环境下增量编译 **3.5 秒**，全套 test+clippy 几分钟内完成。
- 用沙箱 bash 时还要注意：后台任务的 `/tmp` 与当前 shell 的 `/tmp` 可能不是同一个，
  验证日志写到**项目内**（`target/verify.log`）才读得到。

**验证**：`cargo test` 147 passed / 2 ignored，`cargo clippy --all-targets` 退出码 0。

**坑与结论**：

- **`SelectableText` 自己不实现 `Styled`**，没有 `.text_color()` / `.text_sm()` / `.truncate()`；
  样式靠外层 `div` 继承（`request_layout` 走 `window.text_style()`）。所以写法是
  `div().text_xs().text_color(muted).child(copyable(...))`。
- **循环里不能用 `copyable`**：`ListItem::new(id)` 内部只是 `h_flex().id(id)`，不往元素 id
  栈里压，所以同一 `render_item` 里多处 `copyable` 拿到的全局 id 完全相同 → 第 2 行起共用
  第 1 行的选中状态。行内一律 `copyable_as` 带显式 id（`repo-category:{id}`、
  `source-url:{url}`、`detail-tag:{id}:{tag}`）。同一对话框两份实例（分类页/标签页）
  也一样：`assign-note:{kind.label()}`。
- **按钮标签与页面标题不做**：`SelectableText` 会插一层 hitbox，摆在按钮里会把点击抢走。
- `Button::small()` 来自 `Sizable` trait，`settings_view.rs` 少 `Sizable as _` 就报 E0599
  （和上次 `.ghost()` 缺 `ButtonVariants` 是同一类坑）。
- clippy 的 `cloned_ref_to_slice_refs`：`&[x.clone()]` 应该写 `std::slice::from_ref(&x)`。

**真机验证**（比之前更进一步）：用 `NGY_FAV_HOME=E:\tmp\ngy-smoke\cfg` 起一次生成真库，

**验证**：`cargo test` **169 passed / 0 failed / 2 ignored**，`cargo clippy --all-targets` 无警告。

## 仓库筛选增加「编程语言」「标签」两个维度

需求：仓库的筛选，要增加编程语言、标签。

**三个维度之间是且**：分类（单选，选上级=整棵子树）、语言（单选）、标签（**多选、都得有**，
跟 GitHub 的 label 筛选一个意思）。

**做法**

- `RepoQuery` 加 `language: Option<String>` 与 `tags: Vec<String>`，`RepoQuerySpec` 对应加两个；
  顺手把「有没有筛过」收进 `RepoQuery::has_filters()`，`is_really_empty` 改用它。
- SQL（`db/repos.rs::build_filter`）：语言 `r.language = ?` —— **精确相等，不用 `LIKE`**
  （`Go` 不该把 `Gosu` 也捞进来）；标签**每个一个 `EXISTS`**，几个标签就是「几个都得挂上」。
- `Library::{language_rows, tag_rows}` 出筛选清单（新结构 `FacetRow { name, repos }`），
  计数从内存镜像里数——口径跟分类一致：**数字是全库的**，回答「选它会看到几条」。
  语言按数量降序（同数量再按名字，顺序才稳定），标签按词表顺序。空白的语言不算一种语言。
- delegate：`set_language` / `toggle_tag` / `set_tags` / `clear_filters` / `has_facet_filters`。
  **`set_tags` 会排序（按 `name_key`）**：顺序不跟点击走，否则「先点 A 再点 B」与反过来是
  两份不相等的条件，「条件没变就不重查」失效，SQL 参数顺序也成了看运气。
- 视图：`render_filter_bar` 扩成三个下拉 + 「清除」。一维没得筛就不摆那一维，三维都没得筛
  整条不画（全库只有一种语言时，筛它等于不筛）。语言/标签在词表里消失时在 `sync_page`
  里摘掉并回第一页——跟「分类被删」同一套。

**picker 改成 builder + 多选行**

`Picker::new(prefix, icon, label).rows(..).selected(..).accent(..).stretch().on_pick(..)
.into_element()`（原来的 `category_picker` 有 7 个位置参数）。标签要多选，而「点完收不收」
是**行**的事而不是模式：`PickerRow.close` + `keeping_open()`，「不限」那行留 `true` 收尾。
picker 层因此没有「多选模式」这个概念。顺手加了 `accent`（筛上了把按钮点亮，走 `Button::primary`）。

**验证**：`cargo test` **197 passed / 0 failed / 2 ignored**（181 → 197：db 4 条、library 2 条、
delegate 5 条、picker 1 条、`repos_view` 3 条 + 界面 1 条），`cargo clippy --all-targets` 无警告。
界面那条真点了一遍：Rust 单选点完就收 → 标签多选点完不收 → 两维叠起来是且（0 条）→
「不限」清标签 → 「清除」把语言也归位。本批未提交。
