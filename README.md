# ngy-fav-project

一个管 GitHub 仓库收藏的小程序：手工添加或从 trending 自动发现，顺带把仓库的描述和创建时间补齐。
桌面界面用 [gpui-kit](https://crates.io/crates/gpui-kit) 写。

```bash
cargo run
```

## 它做什么

**项目管理** — 每个仓库记这几个字段：仓库名（`owner/repo`）、地址、原始描述（抓自仓库页 About）、
汉语描述（人工填，可选）、发现时间、创建时间。汉语描述填了就在列表和详情里优先显示。

**分类与标签** — 一个仓库最多属于**一个**分类，可以挂**任意多个**标签。分类是单选，
详情面板里画成一个色块（颜色由名字算出来，同一个分类到哪都是同一个颜色），改分类时用下拉树；
标签横着铺一排。**筛选用得到的东西就这三样**（分类、语言、标签），再加一个搜索框，
搜索还能命中描述。
两者规则一样，但在侧栏里是**两个独立页面**（「分类」和「标签」），各自管自己的词表。
页面里每一行都能上下挪，摆成自己顺眼的顺序——顺序只影响怎么摆，跟归属无关。

**分类是一棵树** — 分类有上级和下级，可以点着上级在它下面直接新建子分类。
选中上级就等于同时属于它下面的所有分类，按上级筛选会把它整棵子树里的仓库都筛出来。
填的时候还是写 `开发/前端` 这种路径，它会被逐级解析成树上的节点（缺的上级顺手建出来）。

**筛选条是三个下拉** — 分类、语言、标签各占一个，横着排一行（窄了就折行），
筛上了的按钮会点亮，旁边多一个「清除」把三个一起归位（搜索框不在其中，那归它自己）。
三者之间是**且**：分类筛完、语言再筛、标签还得都挂着。

- **分类**是一棵**缩进排出来的树**（层级不写进名字里，靠缩进看），选上级等于选它整棵子树。
  早先那排色块一多就要折成好几行，而 `AI Agent/Tools` 这种路径在折行里读不出层级。
- **语言**是扁平枚举，**单选**，按仓库数从多到少排（`Rust · 12` 排在 `Go · 2` 前面）。
  没有「未标注语言」这一项：没语言是元数据还没补上，属于「待补全」那件事。
- **标签多选**，选中的都得挂着（跟 GitHub 的 label 筛选一个意思）。所以标签那一维的行
  **点完不收**——挂着 cli 之后还得接着挂「待读」；只有「不限」是收尾的那一下。

每个下拉上的数字都是**全库**的计数（跟「选它会看到几条」对得上），不是「在当前这堆条件里
还剩几条」——后者要按维度交叉重算，数字会一直变，反而看不出该点哪个。

**筛选项在词表里消失了就自动摘掉** — 分类被删、语言因为重新抓元数据而不存在、标签被摘掉，
这些条件都会在查库之前被清掉（并回到第一页）。留着它们只会让列表一直空着，而用户看不出为什么。

**给一个仓库改分类是同一个下拉框** — 在仓库详情里点「分类与标签」，分类那一栏不再是一排
色块，而是同一棵下拉树（只是不带数量、最前面多一条「不分类」）。两处共用
`taxonomy/picker.rs`：它只管「把行摊出来」和「点一行之后把 key 交出去」，
key 是什么意思、点完收不收起（见 `PickerRow::close`）由调用方说了算。

**列表分页** — 仓库列表按页从数据库取，搜索、三个维度上的筛选、翻页都落在 SQL 里，
不会把整个库读进内存再筛。

**勾选与批量改分类** — 列表每一行左边有个勾选框；勾上之后上方多出「改分类」和「清空」。

- 勾选**跨页、跨筛选条件地留着**：勾了就是不希望它因为翻个页就消失。所以「已选 N 个」
  里可能有当前筛不出来的——那是用户在别的条件下勾的。仓库真的被删掉时才会摘掉。
- 上方那个方框是**三态**的（全勾上 / 勾了一部分 / 一个没勾）。组件库的 `Checkbox` 只有
  前两种样子，所以这里用方框图标（`SquareCheck` / `SquareMinus` / `Square`）自己摆了一个：
  筛出 200 条只勾了 3 条时，摆一个空方框或满方框都是假话。
- **「全选」选的是筛出来的整批**，不是当前这一页——分页只是取的时候分。所以它单独走一次
  不带 `LIMIT` 的 `SELECT id`；换个筛选条件，它跟着变。
- 点「全选」时如果整批已经都在勾选里，反过来把**匹配的那些**摘掉。摘的不是整个勾选集合：
  里面有别的条件下勾的，那不属于这一次点击的范围。
- 勾选跟「详情面板正在看哪一个」是两件事，**点勾选框不会把详情面板换过去**（勾选框外面
  那层挂了 `stop_propagation`，不然连着勾五个就会看见右边来回乱跳）。
- 「改分类」是把这批仓库的分类**都换成所选的这一个**（原来是什么都会被覆盖），**标签不动**。
  整批一个事务写下去；勾选里混了已经删掉的仓库不算错，提示里会说清真改到了几个。
  保存成功后勾选自动清空——这批已经处理完了。

**仓库发现** — 发现源就是一条 URL，规则是「返回结果和 trending 页面长得一样」。默认带一个
`https://github.com/trending?since=weekly&spoken_language_code=`。可以加多个（换语言、换时间窗）。

**后台任务** — 每 5 秒巡检一次，到点就跑一轮发现并入库，已存在的仓库跳过。

**界面上的字都能选** — 列表和详情里的仓库名与地址、描述、分类与标签名、发现源与 URL、
运行记录、错误信息与统计行，都能划选、`Ctrl+C` 复制。

## 界面上的文字都能选

这是 gpui-base 自带的**窗口级**文本选中（`SelectableText` + `Root` 里那层
`TextSelectionLayer`），不用自己实现选中与剪贴板，项目只是在 `shared/text.rs` 里包了一层。
两条规矩：

- **每段文本要有稳定的身份**。选中状态按元素 id 存。最省事的 id 是代码位置（`copyable`），
  但**同一段代码渲染多份时会撞车**——列表的每一行、同一个对话框的两份实例，
  都要用 `copyable_as` 显式给 id（仓库名带 `repo.id`，发现源带 URL），
  否则第 2 行起会共用第 1 行的选中状态。`ListItem::new(id)` 内部的 `h_flex().id(id)`
  **不会**往元素 id 栈里压，所以行与行之间不能指望它来区分。
- **可复制的文字放在可点击的行里没问题**。一开始担心「文本的 hitbox 会把整行的点击吃掉」，
  所以按钮、列表行里都绕着走；实测不是这样——`SelectableText` 的 hitbox 是普通行为
  （`HitboxBehavior::Normal`），gpui 的命中测试会把包含指针的**每一层** hitbox 都算进来，
  父级的 `hitbox.is_hovered()` 照样为真，点击照常冒泡上去。于是「点名字 = 触发整行」和
  「划名字 = 选中文字」可以同时成立（单击是前者，按下拖动才是后者）。
  这条有测试盯着（`shared/text.rs`），免得以后又照着错的理由绕路。
- **只有「这句话是内容，还是控件本身」这一条判断**：按钮标签、页面标题不必做成可选的，
  不是因为会抢点击，而是因为它是控件上的字——划它没有意义。

## 后台任务什么时候动

巡检分两种，别把它们混在一起：

| 触发 | 条件 | 干什么 |
| --- | --- | --- |
| 完整运行 | 距上次抓源 ≥ `interval_minutes` | 抓所有启用的源 → 顺带补一批元数据 |
| 元数据补全 | 没到间隔，但有仓库缺描述/创建时间，且距上次 ≥ 重试间隔 | **只**补元数据，不碰发现源 |

元数据补全单独成轮是有原因的：早先它和完整运行挤在一起，于是每 60 秒就重抓一次 trending，
还把上一次「新增 21 个」的成功记录盖成一次超时失败。

重试间隔默认 60 秒，**连续一轮一个字段都没补上就翻倍**（60 → 120 → 240 → …，封顶 15 分钟）。
GitHub 匿名接口每小时只有 60 次，固定节奏重试几分钟就能把它烧光，之后整点前都补不动。

一轮里同时补 4 个仓库（`METADATA_CONCURRENCY`）。串行补 21 个实测要四十多秒，
全程「运行中」把界面锁住，用户点什么都被拒；并发不改变请求总数，对配额没有额外代价。

### 配额用完就停

撞上配额之后继续发请求不可能成功，只会把「配额几时恢复」这句话重复几十遍，
还把连接和线程耗在必然失败的请求上。所以撞一次就把闸门拉下来。

判据在 `github/rate_limit.rs`，三项任一成立即算撞上：

- `X-RateLimit-Remaining: 0`——主限流，匿名接口撞到的几乎都是它；
- 状态码 429；
- 403 **且**正文提到 `rate limit`——二级限流不带配额头，只能在正文里认。

**光看 403 是不够的**：令牌没权限、仓库被下架也是 403，那些情况等多久都不会好，
把闸门拉下来只会让用户以为程序卡住了。

闸门拉下之后：

- 巡检直接返回「没活干」，连**一轮完整运行都不起**——不只是停掉补全那一段；
- 轮内已经在飞的那几个请求拦不回来（最多 `METADATA_CONCURRENCY` 个），
  但**还没启动的一个都不会发出去**，办法是在每个请求前先问一次闸门；
- 恢复时刻到了自己就重新开始，不需要用户去点一下。

恢复时刻取自 `X-RateLimit-Reset`；二级限流不给这个头，按经验等一分钟。闸门最多
拉一小时，万一那个头被中间设备改写成远期时间，不至于把发现功能永久锁死。

配额掐断的那一轮**不算**「无进展」，所以不会叠加到补全退避上——否则恢复时刻到了
还要再多等一轮，用户会以为坏了。

用户主动点「立即运行」或详情页的刷新会先把闸门松开：他多半刚在设置里填了令牌
（配额从 60 涨到 5000）。真要是没恢复，第一个请求 403 回来会立刻再把它拉上，
代价只有一个请求。

```
  app.rs               AppShell：侧栏导航五页 + Root overlay
  library.rs           领域数据唯一持有者：内存镜像 + 写穿数据库
  db/
    mod.rs             连接与错误类型（open / transaction / PRAGMA）
    schema.rs          表结构与版本迁移（PRAGMA user_version）
    repos.rs           仓库表的读写：分页、搜索、按分类/语言/标签筛选都在 SQL 里
    taxonomy.rs        分类树与标签表的读写
    merge.rs           把另一个库并进当前库（移动数据时用）
    sources.rs         发现源与设置
    legacy.rs          把旧版 library.json 导进来（只在空库上跑一次）
  shared/
    net.rs             阻塞 HTTP（ureq）桥成 async，走独立 OS 线程
    store.rs           位置文件解析 + 数据目录里的文件清单 + 旧文件留档
    relocate.rs        搬文件：单个/整批、覆盖与否，跨盘退回复制

  github/
    trending.rs        trending 页面解析（纯函数）
    repo_meta.rs       About 描述 + 创建时间，两路并行抓
    rate_limit.rs      配额判据 + 熔断闸门（撞上就停，见上面「配额用完就停」）
  repos/
    model.rs           Repo 领域模型 + 分页查询的条件与结果形状
    list_delegate.rs   列表 delegate（只记条件、当前页、选中与勾选，查库由视图做；含行里的勾选框）
    repos_view.rs      仓库页（含翻页条、筛选条：分类/语言/标签三个下拉，与批量操作条）
    add_repo_dialog.rs / edit_description_dialog.rs / taxonomy_dialog.rs
    bulk_category_dialog.rs   整批改分类（勾中的一批换同一个分类，标签不动）
  taxonomy/
    model.rs           名字与路径语法（清洗、比较、颜色种子），纯函数
    tree.rs            内存里的分类树：父子关系、铺平、子树，纯函数
    chip.rs            分类与标签的色块
    picker.rs          下拉选择（缩进的分类树或扁平枚举；筛选条与两个改分类对话框共用）
    taxonomy_view.rs   「分类」页 / 「标签」页（同一种视图的两份实例，`kind` 决定管哪个词表；含拖拽排序）
  discovery/
    model.rs           发现源、运行记录、设置
    runner.rs          后台调度（巡检、计划、执行）
    sources_view.rs    发现页
  settings/
    settings_view.rs   设置页
build.rs               构建时把 assets/icon.ico 嵌进 exe
assets/icon.ico        应用图标
tools/make_icon.py     图标生成脚本（改图标时才需要跑）
```

分层的几条约定：

- **网络与解析分离**。`github/trending.rs` 和 `repo_meta.rs` 里的解析都是纯函数，
  拿字符串进、拿结构体出，所以能直接单测（测试用的是真实抓下来的 HTML 片段）。
- **`Library` 是数据的唯一持有者**。视图不缓存仓库，只观察它；仓库列表按页从库里取，
  不把整库读进内存。
- **先写库，成功了再改内存**。反过来做，写失败时会在内存里留下一份下次启动就消失的假象。
  分类树上的操作连着改一批节点，写成功之后直接整批重读（那张表只有几十行）。
- **`RunPlan` 是快照**。一轮开始时把配置读成值，抓取途中用户改设置不影响本轮。
- **时间只从 `shared/clock.rs` 出**，一律 `i64` Unix 秒。

## 分类与标签的几条规矩

词表（有哪些分类、有哪些标签）和归属（哪个仓库属于谁）是分开的两件事：词表由侧栏的
「分类」和「标签」两个页面各管一半，归属在仓库详情里点「编辑」设置。

- **名字就是身份**。比较时忽略大小写（`AI` 和 `ai` 是同一个），存下来的是第一次出现的写法。
  名字里的连续空白会被压成一个空格，超过 40 个字算误输入。
- **一个仓库最多一个分类**。分类是单选，所以必有「不分类」这一项；删掉一个分类，用它的仓库
  回到未分类，**仓库本身不会被删**。
- **标签可以挂任意多个**，顺序按词表排，不按点击顺序——同一组标签在任何仓库上看起来都一样。
- **标签改名会跟着改引用**。改标签名时，所有挂着它的仓库会一起改，不用手工重挂。
  分类改名则**完全不用碰仓库**：仓库上存的是分类节点的 id，不是名字（见下）。
- **归属只认词表里已有的分类/标签**：往仓库上写一个不在词表里的名字会被拒绝（返回 `false`，
  什么都不改）。界面上的「新建」走的是「先加词表、再挂上」，所以正常路径碰不到这个拒绝。
- **批量改分类只动分类**。整批是**一个事务**里的一条 `UPDATE ... WHERE id IN (...)`，
  中途出错整批回滚，不会留下改了一半的一批；标签一个都不碰。返回的是**真被改到的条数**
  （勾选里混了已经删掉的仓库时会比勾的少），提示里照实说。

### 分类是一棵树

树上的一级知道自己挂在哪一级下面，父子关系是**存出来的**（`categories.parent_id`），
不是从名字里的斜杠猜出来的。好处很直接：

- **改一个分类的名字只影响它自己**。不用顺着名字去改写一串引用，也不存在「改了一半」的中间状态。
- **挪一棵子树只改一个 `parent_id`**。子分类与仓库都跟着走，不需要重命名。
- **仓库上存的是节点 id**（`repos.category_id`），所以分类改名、搬家都不碰仓库那一行。
  分类没了（删掉）时，仓库的 `category_id` 被置空，回到未分类。

规则：

- **名字里可以带 `/`，但那只是名字**。界面上填的还是 `开发/前端` 这种路径，
  它对应的是一条「从顶层走到它」的路，会被逐级解析成节点——缺的上级顺手建出来。
  分隔符是 `/`（全角 `／` 在清洗时会被换掉），最多 6 级，每级不超过 40 个字。
  `开发//前端` 这种中间空着一级会被判为误输入，而不是悄悄给你改成 `开发/前端`。
- **同级不能重名，不同级可以**。`工具/前端` 和 `开发/前端` 是两个不同的分类，
  但同一级下面不会有两个「前端」。
- **同级之间按建立顺序排**，不按名字的码点排。新分类接在末尾，改个名字不会换位置。
  顺序可以自己摆：**把一行拖到另一行的上半或下半**，落点会画一条线，松手就插到那一行的
  前面或后面——中间隔着几格都是一步到位，不用一格一格挪。落点只认**同级**的行：
  跨层换的是上级，那是改名（把完整路径填进去）的活。每行右边那两个上移/下移按钮还留着，
  用来做前后一格的精调；已经在两头的按钮是灰的。
- **改名框里填的是完整路径，所以改名同时也能搬家**：把 `开发/前端` 改成 `工具/前端`，
  就是把它连同子分类一起挪到 `工具` 下面。改到自己的下级里会被拒绝（树会成环）。
  上级真的换了才挪位置；只是改名字的话，它还在原来那一格。
- **删除是连子树一起删**：删掉 `开发`，它下面的分类也都不在了，那些仓库回到未分类。
  删一个叶子不影响它的上级。
- **计数含子树**。「开发」旁边写的仓库数，包含它下面所有分类里的仓库。

## 数据

默认 `%APPDATA%\ngy-fav-project\library.db`（macOS/Linux 走 `Application Support` / `XDG_CONFIG_HOME`）。
设 `NGY_FAV_HOME` 可以整个换掉目录。默认位置在 C 盘，容易被系统盘占满，
所以设置页里可以直接把数据搬到别的盘（见下面「数据放在哪」）。一个 SQLite 库文件，六张表：

| 表 | 装什么 |
| --- | --- |
| `repos` | 仓库本身，`full_name` 的小写形式是主键 |
| `categories` | 分类树：`parent_id` 指向上级，`position` 是同级内顺序 |
| `tags` | 标签词表，扁平 |
| `repo_tags` | 仓库与标签的多对多 |
| `sources` | 发现源与它们的最后一次运行记录 |
| `settings` | 一行配置（自动发现、间隔、批次、令牌） |

几条实现上的取舍：

- **外键显式打开**（`PRAGMA foreign_keys = ON`）。分类的级联删除完全靠它，不同步打开
  就等于没有约束：删掉 `开发` 时它的子树不会跟着走，仓库的 `category_id` 也不会被置空。
- **`name_key` 列存小写化的名字**。SQLite 的 `lower()` 只认 ASCII，名字可能是任意 Unicode，
  所以小写化在 Rust 里做（`taxonomy::model::name_key`），比较走这一列。
  同级唯一用一条 `UNIQUE INDEX ... ON categories(ifnull(parent_id, 0), name_key)` 兜住。
- **`PRAGMA user_version` 是 schema 版本**。库比程序新时硬失败、不写入，并在界面顶部说明，
  免得把不认识的表结构改坏。`journal_mode = WAL`、`synchronous = NORMAL`。
- **搜索的 `LIKE` 会转义** `%` / `_` / `\`（`ESCAPE '\'`）。不转义的话搜 `a_b` 会命中 `axb`。
- **列表按 `LIMIT/OFFSET` 取**，总数另查一次 `COUNT(*)`。排序是
  `discovered_at DESC, full_name ASC`——翻页需要一个稳定的全序，
  否则同一条记录可能在两页里各出现一次。一页 50 条（`DEFAULT_PAGE_SIZE`）。
- **「全选」那条 `SELECT id` 不带 `LIMIT`**。它要的是筛出来的整批，跟着列表的排序走；
  一批改分类也是拿这些 id 一条 `UPDATE` 写下去。拼 `IN (...)` 之前先拦空列表——
  sqlite 里 `IN ()` 是语法错误，不是「什么都不匹配」。
- **页码越界会回退**。站在第 3 页时筛掉一半仓库，查询会退回最后一页，
  而不是让用户对着一片空白自己点回去。

### 旧版 `library.json`

以前数据在一个 JSON 文件里。**只在全新空库时**会去看同目录有没有 `library.json`：
有就整批导进来（一个事务，中途失败不留半份数据），成功后把旧文件改名留档成
`library.legacy-<时间戳>.json`。库里有数据时完全不碰它，导过一次也不会再导第二次。

导进去之后的结果在界面顶部说明（「已把 library.json 迁移进数据库：…」）。
旧文件读不懂时会以空库启动、保留原文件不动，并把原因写在顶部的提示条里——宁可看起来是空的，
也不要静默丢数据。

## 数据放在哪（可以搬）

设置页的「数据位置」一栏选个目录，点确认就把库搬过去，**当场生效**，不用重启。
搬完旧位置的文件就不在了；「打开所在文件夹」用来回答「搬哪去了」。

位置本身记在一个**不跟着搬**的地方：`%APPDATA%\ngy-fav-project\location.json`（几字节）。
挪不动数据时它里面会多出一个 `pending_move`（从哪搬、怎么搬），
下次启动先把这件事做完再打开库——**先记意图、再动文件、最后改路径**，
任何一步断掉（拔盘、断电、文件被占）都还能补完。

搬法分两种，看目标位置有没有东西：

| 情况 | 做什么 |
| --- | --- |
| 目标目录是空的 | 直接搬家。文件级 `rename`，跨盘时自动退回复制 + 删源 |
| 目标目录已经有库 | 不替用户做主，摆三个选项让他挑 |

三个选项的差别（`relocate.rs` 里就是这三种策略）：

| 选项 | 新位置的数据 | 旧位置的文件 | 合并规矩 |
| --- | --- | --- | --- |
| 仅用新位置 | 保留 | **留在原处**（自己删） | 不合并 |
| 移动并覆盖 | 被旧数据盖掉 | 搬过去、原地不留 | 不合并 |
| 移动并合并 | 是主人，留下 | 搬过去、原地不留 | 见下 |

**合并时新位置是主人**：仓库按 `full_name`（小写后）对上就保留新位置那份，没有再补进来；
分类**按路径**合并（两个库的自增 id 之间没有关系），同级同名的合成一个；
标签按名字（忽略大小写）；发现源按 URL。**设置不动**——用户刚在新位置调过的参数不该被翻回旧值。

几条实现上的坑：

- **`-wal` / `-shm` 要跟着走**。它们和主库文件是一套，漏了就等于拿半个数据库启动。
- **覆盖别人的库之前先删掉它的 `-wal` / `-shm`**（`store::discard_sidecars`）。
  否则新库第一次打开会拿一份对不上的 WAL 去恢复，可能把刚写进去的数据改坏。
- **合并要在两个连接都活着的时候做**。SQLite 的 `ATTACH` 不能跨连接共享，
  而这个程序是单连接模型，所以合并是「把源库读成 Rust 值，再对目标库开一个事务逐条 `INSERT OR IGNORE`」。
- **搬不动就不装作搬了**。文件被占之类的原因导致失败时，回滚到原来的位置继续用，
  标记留着下次启动再试，并在界面上说明——不会留下一个「指向空目录」的配置。
- **这一栏的语义是「能做到就现在做，做不到下次启动补」**，不是「让用户选重启」。
  绝大多数情况选完目录当场就搬完了；真正搬不动的那些会被下一次启动捡起来做完。

## 图标

`assets/icon.ico` 是提交进仓库的成品，`build.rs` 在构建时把它嵌进可执行文件。
Windows 的窗口与任务栏图标取自 exe 的资源段（gpui 的 `WindowOptions::icon` 只对 X11 生效），
所以必须在构建这一层做。同一份资源里还写了文件属性用的版本信息，版本号跟着 `Cargo.toml` 走。

只改代码不用管这里。要换图标就编辑脚本再跑一次：

```bash
python tools/make_icon.py     # 依赖 Pillow
```

脚本在 4 倍尺寸上绘制再降采样，所以边缘自带抗锯齿，不必手工描边。

两个踩过的坑：`build.rs` 自己扫 `Windows Kits\10\bin` 找 `rc.exe`，不走 winresource 默认的注册表查询
（那条路会调 `reg.exe`，在受限环境里会被安全策略直接拦掉）；找不到 SDK 时只发 warning 不阻断构建——
图标是装饰，不该让整个项目编译不过。

## 已知约束

- **匿名接口 60 次/小时**。一个仓库要消耗 1 次（拿创建时间）。21 个仓库要等 3 轮才补完。
  在「设置」里填一个 GitHub 令牌后是 5000 次/小时，界面会显示剩余配额。
  用完就整轮停住，恢复时刻由响应头给出（见上面「配额用完就停」）。
- **令牌不需要任何权限**。设置页那一栏旁边有「去申请」，直接打开 GitHub 的令牌页面。
  classic 不勾任何 scope 时只能读公开信息，fine-grained 的「公开仓库只读」是令牌自带的，
  两条路都够用——本项目只读 `/repos/{owner}/{repo}`，别去勾 write 一类的权限。
- **trending 页面结构变了会报错**，不会静默返回空列表——空列表会被上层误读成「本轮无新项目」。
- 解析规则对着当前页面写（`article.Box-row`），GitHub 改版就需要跟着改。

## 测试

```bash
cargo test                                  # 229 个，离线
cargo test probe_real_metadata -- --ignored --nocapture              # 联网探针，打印每个仓库的耗时与失败原因
cargo test probe_rate_limit_detection -- --ignored --nocapture       # 联网探针，拿真实 403 验证配额判定
```

联网探针默认 skip（会消耗配额），用来回答只有真实网络能回答的问题。第二个探针在配额
还有剩时只打印一行、不做断言；真要它下结论，得等到本机配额恰好用尽——那时它会确认
响应头一路传到了闸门，并打印恢复时刻。

HTTP 层没有联网的部分用**本机 stub 服务**测（`shared/net.rs`）。撞配额时那些
`X-RateLimit-*` 头挂在 403 响应上，而「非 2xx 也把头交出来」这件事只有走一遍真实 HTTP
才说明问题——mock 掉传输层就把要验证的东西一起 mock 掉了。

### 界面也能测（无头窗口）

界面在开发环境里截不到图（沙箱看不到应用的窗口），但**不需要截图**：gpui-kit 的测试台
（`#[gpui_kit::test]` + `gpui_kit::test` 里的 `TestWindowExt`）能在无头窗口里渲染真实的
界面、按元素 id 点击、读回状态与布局。所以「只有跑起来才说得清」的那部分也有测试：

- `repos_view.rs`：点开分类下拉框 → 菜单出现且挂在按钮下方 → 点「开发/前端」这一行 →
  筛选条件落到 delegate 上、列表条数从 3 变 1、菜单自己收起来 → 再点开换成「未分类」。
  另一条盯语言与标签：语言是单选（点完收）、标签是多选（点完留着、连点两下），
  两个维度叠起来是**且**（Rust + 另一个标签 → 0 条），「不限」与「清除」各自把条件归位。
  还有一条盯勾选：点行里的勾选框只勾上、**不**把详情面板换过去（那是「点这一行」的事），
  一个都没勾时不摆操作按钮，「全选」勾的是筛出来的整批（换个筛选条件它跟着变）、
  已经全勾上时再点一下就是取消，「清空」清的是同一件事。
- `bulk_category_dialog.rs`：在下拉树里选一个分类落到草稿上；保存那一下整批真写进库，
  提示里说清改到了几个（勾选里混一个已经删掉的 id → 条数会比勾的少）。
- `taxonomy::picker`：同一个下拉组件自己的一组用例（点开 → 点一行 → key 交给回调 →
  菜单收起；以及 `keeping_open` 的那些行点完不收）。
- `taxonomy_view.rs`：在「分类」页把一行拖到另一行上——`window.drag` 走的是真实指针派发，
  落点认「指针落在目标行的哪一半」，所以顺序真的跟着换、也真的写进了库（子分类跟着上级
  一起走，标签页动的是它自己那张表）。另外按上移/下移按钮也跑了一遍（已经在两头的按下去
  什么都不改），还有一个管「落点接不接」的纯函数：同级、不是自己、指针真在这一行上。
- `taxonomy_dialog.rs`：在下拉树里选一个分类，草稿上的 `category` 真的跟着变——
  保存时被写进库里的正是它。
- `shared/text.rs`：点在可选中的文字上，外层那一行的点击照样收到。

用起来要记住四件事（都在测试里有样子）：

- **要按 id 找的元素得挂 `.test_support()`**（`gpui_base::TestSupportExt`）。没开
  `test-support` 特性时它是恒等函数，所以生产代码里留着没有代价。`Button` 之类
  `RenderOnce` 的组件挂不上，需要包一层 `div` 给它一个身份。
- **窗口更新闭包交给你的视图类型被抹成了 `AnyView`**（拿不到字段），所以要自己留一份
  `Entity<T>`；而窗口的根必须是一个自己实现了 `Render` 的类型，`Entity<T>` 不算。
  更省事的做法是 `cx.add_window_view(...)`，它把 `(Entity<V>, &mut VisualTestContext)` 直接给你。
- **对话框的正文没法这样点**：`open_dialog` 的正文排在 `Root` 的 deferred 层里，
  无头窗口按 id 找不到它（对话框确实开了，但元素不在可观测的元素树里）。要测正文，
  就把那段正文实体（比如 `AssignmentDraft`）直接当窗口根渲染——外壳是组件库的事。
- 这个特性是 dev-dependency 里开的（见 `Cargo.toml`），不进最终 exe。

其余能被测试盖住的部分仍然挤在纯函数与存储层：名字规则、分类树的父子与铺平、词表增删改与同级排序、
归属与筛选、分页与 `LIKE` 转义、旧文件迁移、配额判据与巡检短路。
列表的 delegate 也刻意做成不碰数据库的纯状态（条件归它、查库归视图），所以那些
「换搜索词要回到第一页」之类的规则同样有测试兜着。

**搬数据这件事也整套在测试里**：`relocate.rs` 逐个验文件的搬/留/跨盘回退，
`merge.rs` 验两边合并的取舍（谁当主人、二次合并不动、设置不回来），
`library.rs` 里那组用例按「空目标 / 原地 / 三种策略 / 失败回滚 / 下次启动补做」跑一遍，
用的是临时目录里的真库，不是 mock。
